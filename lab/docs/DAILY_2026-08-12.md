# TFLab 日报 — 2026-08-12

## 引言

恶意流量检测的核心难题在于**无法有效区分恶意流量与正常流量**：攻击者通过
加密通信（WebShell、C2、隧道、RAT、APT 武器）刻意把恶意行为伪装成正常网络
活动，两类流量在可观测层面高度重叠。传统基于 **CIC 流特征（CICFlowMeter 式
聚合统计）**的方案在此问题上表现不佳——流特征是对整条流的统计聚合（包长均值/
方差、间隔统计、标志位计数等），**丢失了真正有判别力的信息**：其一，包序列与
结构信息（"连续 4 个大块请求后再响应"与"一问一答交替"可算出几乎相同的统计值，
恰恰是这种时序结构区分着 WebShell 与正常浏览）；其二，跨流行为信息（爆破/扫描
这类"同一来源在短窗口内发起大量连接"的信号在单流聚合里根本不存在）；其三，
加密长连接/UDP/心跳型工具在固定流窗口下难以对齐。结果是恶意与正常流量在 CIC
特征空间中混叠严重，误报与漏报难以两全，方案无法落地。

针对"无法区分恶意与正常"这一核心问题，本项目**重新设计了整条数据链路**：从
原始抓包直接提取**密文侧信道事件序列**（方向/包大小/到达间隔 token）+ **流级与
跨流行为特征**（TLS 结构、载荷分布、时间节奏、同端口突发、端口扫描等），并采用
**规则探针 + Transformer 流分类器双通道**：规则保证已知模式的高精度与可解释性，
模型负责从未见流量中泛化出恶意信号。两条通道在同一套特征管线上实时运行，
兼顾区分度、实时性、可解释性与泛化能力。

## 一句话总结

用**本机真实流量**作为负样本，把规则误报压到 0、ML 真实流量误报压到 **0.75%**，
并把训练迁移到远程 RTX 5090（共享 GPU）上跑通，全程 61/61 场景回归保持全绿。

## 分块进展

### 1. 规则通道：真实流量补规则

- 本机 `en0` 抓包约 60s（15679 包 / 133 流）作负样本金标准，全规则跑出 **48 条误报**。
- 逐条定位：natpass/stowaway/gost/suo5/sish/platypus/metasploit 规则过泛，
  命中真实流量的 IM 心跳、短 TLS、页面并发。
- 收紧方式：natpass 加 protobuf 字段签名、stowaway 要求 16B 认证交换、gost 要求
  websocket 升级头、sish 要求 SSH banner、suo5 限定 TLS + 小服务端首包、
  platypus/metasploit 要求双向节奏对称；gost 中继改按同端口聚合、
  suo5 JA3 随机化改同端点聚合、meterpreter 突发限小响应小 ClientHello。
- 结果：真实流量 **48 → 0 误报**；收紧后全量回归 **61/61 通过**。

### 2. ML 训练：迁移远程 GPU + 数据扩充

- 远程部署：`ssh sr@172.16.88.180`（RTX 5090 32GB，系统已有 torch 2.9.0+cu128），
  代码 + 86 个流量 pcap 同步到 `~/tflab`。
- 训练提速：数据张量一次搬 GPU、batch 128→512、`torch.compile`、
  早停显示 val_auc 且要求显著改善；6 模型从 2.5 分钟降到约 1 分钟。
- 注意：该 5090 是共享机（被其他用户的 VLLM 占 24GB），真实速度仍受挤占。

### 3. 数据：真实流量采集（本机 + 自造 API 流量）

- 共抓 **4 段本机真实流量（1471 流）**：real_traffic（185）、real_traffic2（320）、
  real_traffic3（231，API 轮询/JSON/POST/下载）、real_traffic4（434，大包上传/流式）。
- 自造多样化 API 流量：httpbin/jsonplaceholder/GitHub/Open-Meteo/reqres/wikipedia/
  cloudflare 等，覆盖 GET/POST/大文件下载/重定向/延迟接口。
- 正常生成流量扩到 13 种模式（含探测状：健康检查/SSH 抖动重连/合规爬虫/浏览器并发/
  DNS 风暴/短 TLS 同步/失败连接/短 HTTP/UDP 应用）。

### 4. 特征工程（含一次失败实验）

- 新增 6 特征：tls13、ClientHello/ServerHello 大小、请求响应比、最大记录、estab。
  归因确认 **ch_len + req_resp_ratio** 是识别正常流量的主要功臣。
- 尝试再加 distinct_dsts（同源目的数）+ burst_var：分布分离度好（真实 0.47 vs
  恶意 0.03），但小数据下模型边界漂移，误报反而 0.99%→2.4%，**回滚到 15 维**。
- 结论：数据量是瓶颈，加特征不是降误报的灵丹妙药。

### 5. 误报/漏报分析

- 随机分割测试集（1835 流）：**3 误报 / 8 漏报**。
- 3 条误报全是同一类：**非 TLS 短 HTTP 到 :80**（700B 请求 / 350B 响应），
  与 webshell 的 HTTP 形态在流量层几乎不可分。
- 8 条漏报全是 n=1 单流，特征是"长得像正常"：TLS1.2 均衡长会话、非 TLS 均衡短流——
  这是压误报的代价（误报率↔漏报率权衡）。

## 问题与决策记录

1. **未见工具 recall 波动（C2 0↔1）**：跨模式未见 SYN 扫描在不同早停设置下
   recall 在 0 和 1 之间跳——单次留出方差大，改用工具级 5 折交叉验证。
2. **cap_real_negative 污染**：真实流量副本被当恶意样本进训练集，
   修复为跳过该文件。
3. **5090 慢的根因**：共享 GPU（VLLM 占 24GB）+ 训练循环 CPU 搬运，两者都处理。
4. **torch.compile 权重前缀 bug**：`_orig_mod.` 前缀导致推理加载失败，
   训练返回原始模型修复。
5. **误报压不动的边界**：非 TLS 短 HTTP 与恶意 HTTP 形态同构，只能靠更多
   同形态正常样本 + 阈值调优，无法完全消除。
